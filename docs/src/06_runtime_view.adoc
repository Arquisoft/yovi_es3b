== Runtime View


ifdef::arc42help[]
[role="arc42help"]
****    
.Contents
The runtime view describes concrete behavior and interactions of the system’s building blocks in form of scenarios from the following areas:

* important use cases or features: how do building blocks execute them?
* interactions at critical external interfaces: how do building blocks cooperate with users and neighboring systems?
* operation and administration: launch, start-up, stop
* error and exception scenarios

Remark: The main criterion for the choice of possible scenarios (sequences, workflows) is their *architectural relevance*. It is *not* important to describe a large number of scenarios. You should rather document a representative selection.

.Motivation
You should understand how (instances of) building blocks of your system perform their job and communicate at runtime.
You will mainly capture scenarios in your documentation to communicate your architecture to stakeholders that are less willing or able to read and understand the static models (building block view, deployment view).

.Form
There are many notations for describing scenarios, e.g.

* numbered list of steps (in natural language)
* activity diagrams or flow charts
* sequence diagrams
* BPMN or EPCs (event process chains)
* state machines
* ...


.Further Information

See https://docs.arc42.org/section-6/[Runtime View] in the arc42 documentation.

****
endif::arc42help[]

=== Single Player Game Initialization

[plantuml,"Game Initialization Sequence with Difficulty",png]
----
actor User #87CEFA
participant "Web App" as Web #87CEFA
participant "Game Engine (Gamey)" as Gamey #87CEFA
participant "Bot" #87CEFA

User -> Web: Open app / Join game
Web --> User: Prompt to select difficulty
User -> Web: Select difficulty
Web -> Gamey: Request new game (player info + difficulty)
Gamey -> Bot: Initialize AI players (if any, with difficulty)
Bot --> Gamey: Ready
Gamey --> Web: Return initial game state (YEN + board)
Web --> User: Render initial board
----

**Description**

1. The user opens the Web App and chooses to join a game.
2. The Web App prompts the user to select a difficulty level.
3. The user selects the desired difficulty.
4. The Web App sends a request to Gamey to start a new game, including player info and difficulty.
5. The Game Engine initializes bot players according to the chosen difficulty.
6. Bots report readiness to the Game Engine.
7. Gamey sends the initial game state and board to the Web App.
8. The Web App renders the initial board for the user.

=== Player Move and Bot Response

[plantuml,"Player move sequence (Web App → Gamey)",png]
----
actor User #87CEFA
participant "Web App" as Web #87CEFA
participant "Game Engine (Gamey)" as Gamey #87CEFA
participant "Bot" #87CEFA

User -> Web: Make move
Web -> Gamey: POST /gamey/choose (send game state in YEN)
Gamey -> Bot: choose_move(game_state)
Bot --> Gamey: Coordinates
Gamey --> Web: MoveResponse (JSON)
Web --> User: Update board
----
**Description**

1. The user performs a move in the Web App.
2. The Web App sends the game state directly to the Game Engine (Gamey).
3. The Game Engine selects the appropriate bot.
4. The bot computes the next move.
5. The result is returned directly back to the Web App.
6. The UI updates with the new game state.
